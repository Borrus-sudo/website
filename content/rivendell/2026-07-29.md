HTML Web components are basically the solution to my [[mycelium - wood wide web]] woes of having interactivity, rendered html but not duplicating the content in js. 
The standard web component is more like "SPA". 
The HTML web component is thought of as expanding the span of html elements by expanding the basis set. We can then add interactivity to them as JS is loaded. This is progressive enhancement. The HTML web component is on the "light" side of the DOM. 
It does not use shadow DOM, templates or slots. The goal with HTML web components is to take HTML to its maximum possible limits and then use them to expand it. It is HTML with "superpowers"!

To quote [Hawk Ticehurst](https://hawkticehurst.com/):

> Rather than dynamically generating the component UI at runtime using JavaScript like you would with regular web components, the HTML web component is parsed, rendered, and styled as normal HTML. That HTML will then be seamlessly hydrated once the JavaScript associated with the custom element tag is executed.


It also has been pointed that out that why "web component" and "web component APIs" are slightly different. HTML web components simply use the custom-element web component API majorly to provide for progressive enhancement cause it makes it portable, follows the single responsibility principle and is overall less fragile. Astro uses it to implement its island functionality! Such HTML web components are fully light DOM! The principal takeaway is that HTML web components are HTML first, essentially HTML extension where JS does not own the markup, simply enhances it. The major difference being they provide a beautiful API to do so!

Frameworks like lit provide an API that is built on top of web component APIs to provide the regular component experience. Pretty cool, but I might just use the standard (P)React/Vue/Svelte frameworks. The only major thing I think they provide is interop, but now svelte and vue also support rendering to web components, so I don't the see the need for them now. lit also has the same SSR, hydration, ARIA problems too. With declarative shadow DOM they seem to solve it but I still don't see why is it any better than the traditional frameworks.
However HTML web components are different in the fact that they don't need SSR. They are HTML first and when JS loads, they hydrate the markup i.e add interactivity. 

Enhance.dev is basically takes the concept of html web components and attaches SSR, slots and styling to it whilst staying on the light side of the DOM! They also provide a nice API to hydrate them on the client with powerful primitives to work with it. 
Astro can do what Enhance does too. They support almost every web paradigm whilst being HTML first. HTML ftw! 
WebC are hard to author on its own cause they don't have good ways to handle state. The UI rendering and state still need to be manually plumbed. Traditional frameworks have this solved by default. Hence lit tries to emulate the ideas of traditional frameworks on top of web component APIs. But in doing so, they have the same power and limitations like the traditional frameworks. The power being that "rendering" is mostly a solved issue and limitation being we still require meta-frameworks to effectively handle "data". Like Rich Harris quotes, the future of frameworks is probably going to be more backend (See: async first frameworks). I want to see how this relates to the traditional web stack of using PHP as backend.

Having web-components but with an alpine like API, where the state is in the HTML is a pretty powerful way to solve the "state" problem. Also works pretty well with the hypermedia way of building applications. Not sure how would hypermedia based systems scale. Would they even scale?
