1. Rule of Modularity — Build simple parts connected by clean interfaces.
2. Rule of Clarity — Prefer clarity to cleverness.
3. Rule of Composition — Design programs to work together.
4. Rule of Separation — Separate policy from mechanism, and interfaces from engines.
5. Rule of Simplicity — Keep designs simple; add complexity only when necessary.
6. Rule of Parsimony — Avoid large programs unless simpler approaches demonstrably fail.
7. Rule of Transparency — Make program behavior visible for inspection and debugging.
8. Rule of Robustness — Build reliability through simplicity and transparency.
9. Rule of Representation — Encode knowledge in data to simplify program logic.
	- Data first approach. Get a feel for the data structure and the algorithm becomes obvious.
10. Rule of Least Surprise — Make interfaces behave as users expect.
11. Rule of Silence — Avoid unnecessary output.
12. Rule of Repair — When failure is necessary, report it clearly and promptly.
13. Rule of Economy — Save programmer time, even when that costs some machine time.
14. Rule of Generation — Automate repetitive code creation where practical.
15. Rule of Optimization — Get a working prototype before optimizing.
	- Premature optimization is the root of all evil
	- Premature designing is also the root of all evil. [[Form fits the context]] is pretty similar to this advice. 
16. Rule of Diversity — Be skeptical of claims that one approach suits everything.
17. Rule of Extensibility — Design so future changes can be accommodated.
